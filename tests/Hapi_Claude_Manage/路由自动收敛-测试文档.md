## 1. 需求

原来菜单 7（写入官方 auth.json）只打印一句话：

```
注意: 当前 config.toml 中 model_provider = "custom"，模型请求仍会走该第三方 provider。
官方登录态只影响 Codex 识别到的账号；若想完全走官方，请移除 model_provider 及对应的 [model_providers.*] 段。
```

用户要求改成**自动**且**可逆**：

- 识别到官方登录 / 官方 Key → 自动把 `custom`（及其它第三方路由）从 `config.toml` 移除；
- 恢复第三方时 → 自动把 `custom`（及其它第三方路由）恢复回来。

参考实现：`E:\myrepo\参考\cc-switch`（只在开发机上，不随仓库分发）。

## 2. 参考实现依据（都写明文件 + 函数，别凭记忆）

| cc-switch 位置 | 结论 |
| --- | --- |
| `src/config/codexProviderPresets.ts` 的 `OpenAI Official`（`isOfficial: true` / `category: "official"`） | 官方预设 = `auth: {}` + **`config: ""`**，即官方 = 既没有 `model_provider` 也没有 `[model_providers.*]` |
| 同文件第三方预设（如 `generateThirdPartyConfig`、`Azure OpenAI`） | 第三方 = `model_provider = "custom"` + `[model_providers.custom]` 同时存在 |
| `src-tauri/src/codex_config.rs` `write_codex_live_config_atomic` | 切供应商时只整份写 `config.toml`；`config_text: None`/空 = 官方 |
| 同文件 `codex_live_auth_is_stale_third_party_residue` / `clear_stale_codex_live_auth_after_official_switch` | 切官方后要清理第三方残留凭据（cc-switch 清 `auth.json`，本脚本对应的是清 `config.toml` 里的路由） |
| 同文件 `should_restore_codex_provider_token_for_backfill` | `category == "official"` 时不恢复供应商 token；第三方才恢复 |
| 同文件 `active_codex_model_provider_id` / `is_custom_codex_model_provider_id` / `CODEX_RESERVED_MODEL_PROVIDER_IDS` | 「保留 id」判定与脚本里已有的 `isCustomProviderId` 一致 |
| `src-tauri/src/proxy/providers/codex.rs` 的 `should_send_codex_chat_prompt_cache_key()`（`Some("api.openai.com") => true`） | ⚠️ **用途不是官方供应商判定**（它决定转成 Chat Completions 后要不要发 `prompt_cache_key`）。cc-switch 没有「Codex 官方 host 分类」函数；`is_official_provider()` 只存在于 `claude_desktop_config.rs`（Claude Desktop）。脚本的 `classifyBaseUrl` 是**自行加的保守规则**：host 精确等于 `api.openai.com` 才算官方，写法与该函数的 host 比较形式一致，但**依据是"保守"，不是"照抄 cc-switch 的判定"** |
| 同文件 `codex_provider_table_falls_back_to_official_auth` | 「`requires_openai_auth = true` 且没有 `env_key` / `experimental_bearer_token`」的 provider 表会**回落到 `auth.json` 的官方登录**——这正是「官方登录 + 残留第三方路由」的危害：官方凭据会被发到第三方端点。所以自动剥离是有安全意义的，不只是"路由走错" |
| `src/utils/providerConfigUtils.ts` `isCodexUnifiedSessionProjection` / `hasExplicitNonOpenAiCodexModelProvider` | `model_provider != "openai"` 才算「显式第三方 provider」——官方路由就是内置 `openai` |

cc-switch 有数据库保存每个供应商的 config 文本，所以它切官方时可以整份写空；本脚本没有数据库，
因此**剥离时把被删掉的原文存进暂存文件**，恢复时按原文写回（见 §4.2）。

## 3. 路由判定表（`decideCodexRoute`）

输入：`auth.json` 解析出的模式（`resolveAuthMode`）、`auth.json` 是否有可用官方凭据
（`hasOfficialAccountMaterial`）、本次是否填了新 Key、`base_url` 判定结果、当前 `model_provider`。

| auth.json 模式 | 有官方凭据 | 本次填了新 Key | base_url | 目标 | 动作 |
| --- | --- | --- | --- | --- | --- |
| `chatgpt` / `chatgptAuthTokens` | 是 | 否 | 任意 | **official** | 剥离第三方路由并暂存；本来就没有路由则只提示 |
| `chatgpt` / `chatgptAuthTokens` | 是 | 是 | 第三方 | third-party | 保留/恢复路由，并更新 `base_url` |
| `chatgpt` / `chatgptAuthTokens` | 是 | 是 | 官方 / 无法解析 | **official** | 剥离并暂存 |
| `chatgpt` / `chatgptAuthTokens` | 否 | 是 | 第三方 | third-party | 建路由 / 恢复暂存路由 |
| `chatgpt` / `chatgptAuthTokens` | 否 | 是 | 官方 | **official** | 不建路由（Key 落进 auth.json → apikey 模式，走内置 openai） |
| `chatgpt` / `chatgptAuthTokens` | 否 | 否 | 任意 | legacy | 旧行为：有路由则更新 `base_url`，没有则建默认 custom 模板 |
| `apikey` | — | — | 官方 | **official** | 剥离并暂存（凭据在 auth.json，内置 openai 会用它） |
| `apikey` | — | — | 第三方 | third-party | 保留/恢复路由（第三方端点必须保住它自己的路由） |
| `apikey` | — | — | 无法解析出 host | keep | 不动路由，只提示 |
| `personalAccessToken` / `agentIdentity` / `bedrockApiKey` / `bedrockAccessKeys` / `headers` / 未识别取值 | — | — | — | keep | 不动路由，只提示 |
| 任意（但当前 `model_provider` 是保留 id） | — | — | — | keep | 保持原样：不剥离、不建表（覆盖保留 id 会让 Codex 拒绝加载整份配置） |

补充规则：

- `model_provider = "openai"` 视为官方路由（内置 provider），但**不删这一行**——它语义等同缺省。
- 官方 host 判据：host 恰为 `api.openai.com` → 官方；空值 → 按官方；解析不出 host → `unknown` → keep。
  `https://api.openai.com.evil.com` 不是官方（精确匹配，I9 已断言）。
- **`apikey` 模式不看「有官方凭据」这条捷径**：凭据就在 `auth.json` 里，官方还是第三方只能靠 `base_url` 判断，
  否则中转 key + 中转路由会被误判成官方登录而剥掉。（首版实现踩到了这个坑，已修。）

## 4. 具体行为

### 4.1 剥离（official）

从 `config.toml` 移除三样东西，且都进入暂存：

1. 顶层 `model_provider = "<自定义 id>"` 行；
2. 该 id 对应的 `[model_providers.<id>]` 整段（含段内的 `experimental_bearer_token` 等全部字段）；
3. 顶层 `experimental_bearer_token` 行（如果存在）。

其余内容原样保留：`model`、`[features]`、`[mcp_servers]`、别的 `[model_providers.*]` 段（非当前路由，Codex 会忽略）。
删除后若出现连续空行会收掉一个，避免留下双空行。

### 4.2 暂存文件

- 路径：`~/.codex/hapi_provider_route.json`（`hapi_codex_route_stash_file`），**单个槽位**。
- 写入时 `0600`（node 侧 `{ mode: 0o600 }` + `fs.chmodSync`，shell 侧再 `chmod 600` 一次）。
  它可能带着第三方的 `experimental_bearer_token`，所以按凭据文件对待。
- 结构：

```json
{
  "version": 1,
  "savedAt": "2026-09-19T15:00:00.000Z",
  "providerId": "myrelay",
  "modelProviderLine": "model_provider = \"myrelay\"",
  "sectionLines": ["[model_providers.myrelay]", "name = \"MyRelay\"", "base_url = \"https://relay.example.com/v1\""],
  "extraTopLevelLines": ["experimental_bearer_token = \"sk-...\""]
}
```

- `hapi_show_codex_config`（菜单 1 的预览）会显示 `provider id` / 暂存时间 / section 行数，
  **不打印段内容**（避免把 token 打到终端）。文件存在但格式异常时会显示「格式异常（缺少 providerId / sectionLines）…
  写入第三方 base_url 时会被拒绝（fail-closed）」。
- **读取分三态（`readStash`），不能把 invalid 与 missing 混成一个 null**：
  `missing`（文件不存在）→ 允许退化成「新建 generic custom 模板」；`valid` → 正常恢复；
  `invalid`（JSON 损坏 / 顶层不是对象 / `providerId` 不是可用自定义 id / `sectionLines` 不是字符串数组）→ **fail-closed**。

### 4.3 恢复（third-party）

当 `config.toml` 当前没有自定义 `model_provider` 时：

1. `readStash()` 判定：`invalid` → 打印原因并 `exit 1`，**auth.json 与 config.toml 都不动**
   （此时还没走到任何写盘动作，所以"未改动"是结构性保证，不是巧合）；
2. `missing` → 沿用旧行为，按本次配置新建 generic `custom`；
3. `valid` → 顶层插回 `model_provider = "<暂存 id>"`（provider id 沿用暂存值，保证用户原有的 `query_params` /
   `requires_openai_auth` / `model_context_window` 等字段随段一起回来）；
4. 若该 id 的段不存在，把暂存段原文追加到文件末尾；若段已存在则只补回指针；
5. `base_url` 按**本次填写的 base_url** 更新；
6. 若段里本来就有 `experimental_bearer_token`，则换成本次填写的 Key（沿用既有语义：没填 Key 时不动它）。

对照关系（I10 / I11 就是钉住这条分界线的）：**不存在 stash → 建 generic 可以接受；stash 存在但损坏 → 必须报错中止**。

**空配置走同一条流程（2026-09-19 第二个 blocker 的修复）**：`config.toml` 为空 / 不存在时**不再提前 `exit`**，
而是 `lines = []`、`existingProviderId = ""` 继续走上面这套判定与恢复；只有 `missing` 才落到「按本次配置建段」。
理由：「只写了第三方路由的配置被官方剥离」会把文件变成**空文件**（只剩一个换行），这是生产代码自己造得出来的状态；
空配置若在 `readStash()` 之前提前返回，下一次填第三方 `base_url` 就会绕过暂存、静默建成 generic custom
（I13 用这条端到端现场钉住）。route-only 模式在空配置下仍然只提示「无需同步」并退出（它本来就不恢复路由）。

### 4.3.2 空配置统一后的两处有意输出差异

| 场景 | 旧（`createTemplate` 模板） | 现（统一走 ensure\* 流程） |
| --- | --- | --- |
| 空配置 + 第三方/legacy → 新建 generic 段 | `name = "Custom"` | `name = "custom"`（与「已有 config 里新建段」的写法一致；`name` 只是显示名，不影响路由） |
| 空配置 + 脚本判断不了的模式（如 PAT） | 生成整份 custom 模板 | 只写 `model` + `[features]`，不凭空建路由（与「非空配置 + 该模式」的 keep 行为一致） |

`createTemplate()` 已删除（统一后无调用点）；除上表两处，空配置生成的字段顺序与内容与旧模板一致。

### 4.3.1 官方方向遇到损坏暂存

剥离照常进行（用新的路由内容覆盖那个坏文件），但要打印
`警告: 原暂存文件 … 已损坏（…），本次剥离已用新的路由内容覆盖它。`（I12 断言）。
理由：剥离是权威动作、且坏文件已经不可解析，覆盖不会造成额外损失；但必须让用户知道原来那份已经没了。

### 4.4 触发点

| 入口 | 行为 |
| --- | --- |
| 菜单 1「查看/修改配置」→ `hapi_write_codex_current_config` | 写 `auth.json`/`config.toml` 时按 §3 判定并自动剥离/恢复；进入前多两句提示说明会自动调整路由 |
| 菜单 7「写入/编辑官方 auth.json」→ `hapi_edit_codex_official_auth` | 写完 `auth.json` 后调用 `hapi_sync_codex_route`（route-only）自动剥离并暂存；同步失败返回 1 并红字提示 |
| 菜单 4「切换配置」→ `hapi_switch_codex_profile` | 切完 live 文件后同样调用 `hapi_sync_codex_route`，收敛「官方登录 + 旧配置残留第三方路由」 |
| 菜单 2/3/5（储存/新建/删除配置） | 不改路由（新建的配置在切到 live 时才被收敛） |

`hapi_sync_codex_route` 是 route-only 模式：**只做路由收敛**，不改 `model` / `base_url` / Key，
不碰 `auth.json`，不做备份；`config.toml` 只有内容真的变了才写回（连 `[features]` 都不会顺手补）。
`config.toml` 不存在时直接跳过并提示。

### 4.5 本轮没有改变的行为

- 空 Key 不清空已有的 `experimental_bearer_token`；
- 官方登录 + 空 Key + 第三方 base_url 不会凭空建路由（旧 `preserveOfficialRoute` 语义保留为「official 目标」）；
- 保留 id 不建表、不补 `model_provider`；
- 第 7 项 auth.json 校验（`official` 级）、配置库 `loadable` 级卡点、0600 / mktemp / 编辑器流程都没动。

## 8. 已知边界（本轮有意不做）

1. **单槽暂存**：连续两次剥离只留最后一次（菜单 2 储存/菜单 4 切换可以配合做多份快照）。
2. **菜单 3 新建的配置仍是「按输入生成 custom 模板」**：base_url 填官方端点时也会带 `model_provider`，
   但切到 live 时会被菜单 4 的路由同步收敛掉。
3. **PAT / agentIdentity / Bedrock 模式不动路由**：脚本判断不了这些模式该配哪条路由，只提示。
4. **保留 id 永不剥离**：`ollama` / `lmstudio` / `amazon-bedrock*` 是别的内置后端，误删比留着更危险。
5. **第三方路由的凭据语义沿用既有模板**（`env_key = "OPENAI_API_KEY"`，读环境变量），
   本轮没有改成 cc-switch 预设里的 `requires_openai_auth = true`（那会让 Codex 直接用 `auth.json` 的凭据）。
   恢复时会原样保留用户段里已有的字段，所以从 cc-switch 侧复制的段不会丢字段。
   ⚠️ 反过来也是一种风险：cc-switch 的 `codex_provider_table_falls_back_to_official_auth` 说明
   「`requires_openai_auth = true` 且无 `env_key`/token」的 provider 表会**回落到官方登录**——
   所以把官方登录和 `requires_openai_auth` 的第三方段混在一起时，官方凭据可能被发到第三方端点。这也是自动剥离的价值。
6. **`base_url` 认不出 host 时保持 keep**（不建、不剥），只提示；近似域名 `api.openai.com.evil.com` 已在 I9 断言（此前的缺口已补）。
7. **预览侧的 stash 校验是第二份规则**：`hapi_show_codex_config` 的 `stashProblem()` 与写入侧 `readStash()` 是同规则的
   两份实现（两个独立 node 进程，无法共享代码）。I14 钉住当前三条规则，但**新增规则时两边可能漂移**，
   反例表第 18 条就是这条缺口本身。要彻底消除得把两个 node 段合并成一个程序（本轮没做，改动面太大）。
   上述任一条若要收口，都需要先和 `E:\myrepo\参考\cc-switch` 的对应行为对齐再动。
