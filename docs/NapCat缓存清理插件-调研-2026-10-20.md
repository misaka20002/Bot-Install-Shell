## 1. A. 它到底清哪些路径

### 1.1 目录清单（硬编码，全部来自 `getCleanablePaths`）

根：`nt_data`。Windows 为 `{dataPath}/{uin}/nt_qq/nt_data`（`cleaner-service.ts:11-17`）；
Linux 为 `{dataPath}/nt_qq_{hash}/nt_data`（`cleaner-service.ts:18-59`）。

| 分类 | 实际清理根目录 | 深度处理方式 |
| --- | --- | --- |
| `video` | `Video/<YYYY-MM>/Ori`；无 `Ori` 时退化为 `Video/<YYYY-MM>` | 只认深度 1 的日期目录，然后递归其下（`114-117`） |
| `videoThumb` | `Video/<YYYY-MM>/Thumb`、`Video/<YYYY-MM>/ThumbTemp` | 同上（`118-125`） |
| `ptt` | `Ptt/<YYYY-MM>/Ori` + `Ptt/<YYYY-MM>/OriTemp`；都没有时用 `Ptt/<YYYY-MM>` | `130-137` |
| `pic` | `Pic/<YYYY-MM>/Ori`；无 `Ori` 时用 `Pic/<YYYY-MM>` | **只有 `Ori`，没有 `Thumb`**（`142-145`） |
| `file` | `File/Ori`、`File/Thumb`、`File/ThumbTemp` | 固定三层，无日期层（`148-153`） |
| `log` | `nt_data/log` | 递归（`156-157`） |
| `logCache` | `nt_data/log-cache` | 递归（`160-161`） |
| `ntTemp` | `{hashDir}/nt_temp`（仅 Linux） | 递归（`67-79`、`163-165`） |
| `napCatData` | `{dataPath}/NapCat/data` | 默认关闭（`types.ts:85`） |
| `napCatTemp` | `{dataPath}/NapCat/temp` | 递归（`167-172`） |

每个分类都是**字符串拼接出来的固定目录名**，`Video`/`Ptt`/`Pic` 额外用一组日期目录做一层通配；不存在「扫全树按后缀匹配」的逻辑。

### 1.2 日期层是怎么来的（这也是最容易失效的一环）

```ts
// src/core/utils.ts:36-48
return entries
  .filter(e => e.isDirectory() && /^\d{4}-\d{2}$/.test(e.name))
  .map(e => path.join(basePath, e.name));
```

- 只匹配 **`YYYY-MM`（月）**，不匹配 `YYYY-MM-DD`，也不匹配其它命名（`utils.ts:43`）。
- 只在**深度 1** 找一层；`Pic/` 根下直接躺着的文件、`Video/2025-05/xxx.mp4` 这种「日期目录下的平铺文件」都不会被清到——
  路径列表只包含 `Ori`/`Thumb` 这类子目录，`cleanDirectory` 又不删传入的根（`cleaner-service.ts:180-226`，只 rmdir 递归中的空子目录）。
- 因此，「QQ 换一种目录命名」或「某版本把文件平铺」时，插件会**安静地什么都不清**，不报错。

### 1.3 多账号 / 多实例

- Linux 侧用 `md5(md5(uid) + "nt_kernel")` 反推目录名（`utils.ts:20-24`），在初始化时由 `getLoginList()` 缓存 uin↔uid↔hashDir（`src/index.ts:29-48`）。
- 拿不到 hash 时，退化到**遍历 `nt_qq_*` 取第一个存在的 `nt_data`**，并把它记到当前 uin 名下：

```ts
// src/services/cleaner-service.ts:41-59
for (const entry of entries) {
  if (entry.isDirectory() && /^nt_qq_[a-f0-9]{32}$/.test(entry.name)) {
    ...
    return ntDataPath;   // 第一个命中就返回
  }
}
```

- 多账号时这段是**张冠李戴**风险：A 号清理可能落到 B 号的目录上。issue #4 里用户给的实测路径 `.../_data/nt_qq_9dcdd866eadeb70afd871e08364b931c/nt_db` 也印证了 Linux 布局是 `nt_qq_<32 hex>`。
- 账号枚举在 Linux 上只返回 `uinToUidMap` 里的账号（`cleaner-service.ts:375-393`），**不是**扫盘得到的——同机第二个实例/换号前的残留目录不会被发现。
- 数据根只有一个：`pluginState.dataPath = ctx.core.dataPath`（`src/index.ts:12`），不支持多数据根/多实例。

### 1.4 覆盖漏洞（值得记住的坑）

| 漏洞 | 依据 |
| --- | --- |
| `Pic/<date>/Thumb` 完全不在清理列表（`Video` 有 Thumb，`Pic` 没有） | `cleaner-service.ts:139-145` 对比 `111-125` |
| 日期目录下的**平铺文件**不清，只清 `Ori` 类子目录 | `111-145` + `180-226` |
| `nt_data` 根下的零散文件不清 | 同上 |
| 解压/解密出来的 `{NapCat目录}/cache` 不清（可能是与 `nt_msg.db` 等大的解密副本） | `packages/napcat-common/src/path.ts:29`、`packages/napcat-database/src/reader.ts:336-359` |
| `{dataPath}/NapCat/db_<uin>`（消息库）不清——**这是对的**，但 issue #4 证明用户会误以为「没清干净」 | `packages/napcat-core/apis/database.ts:45`、issue #4 |

## 2. B. `retainDays`：语义、默认值与边界

| 项 | 行为 | 依据 |
| --- | --- | --- |
| 默认值 | `7` 天 | `src/types.ts:87` |
| 判定维度 | **文件 `mtime`**：`now - stat.mtimeMs > retainDays*86400000` | `cleaner-service.ts:188-202` |
| 目录名 | 日期目录只用于**枚举范围**，不参与「新旧」判定 | `utils.ts:36-48` |
| `= 0` | **全删**（任何 mtime 早于此刻的文件都满足）。前端文案也这么写：「设置为 0 则不保留任何文件」 | `cleaner-service.ts:189+198`、`ConfigPanel.tsx:85` |
| 负数 | 数学上等价全删（`now - mtime > 负数` 恒真）；后端没有拦截 | 同左 |
| 小数 | 生效（按毫秒折算），无整数校验 | `cleaner-service.ts:189` |
| 空目录 | 递归过程中把**变空的子目录** `rmdir`；调用方传入的根目录保留 | `cleaner-service.ts:206-219` |
| 失败文件 | 不重试、不计数，只 `log('warn')` | `cleaner-service.ts:203-205` |
| 上限 | 仅 UI `max=365`，非强制 | `ConfigPanel.tsx:91-96` |

补一句扫描侧的差异：`getDirStatsWithFilter` 对 `retainMs <= 0` 做了显式短路（`cleaner-service.ts:246`），而真正删除的 `cleanDirectory` 没有——靠 `now - mtime > 0` 巧合等价。这种「预估与执行两套判断」是后续容易走偏的写法。

## 3. C. 安全性

| 关注点 | 结论 | 依据 |
| --- | --- | --- |
| 路径前缀校验 | **无**。所有路径由 `path.join` 拼出，没有任何 `realpath` + `startsWith(dataPath)` 的包含性检查 | `cleaner-service.ts:91-175` 全文 |
| 符号链接逃逸 | 遍历时 `readdirSync({withFileTypes})` 的 `isFile()/isDirectory()` 对 symlink 均为 false，**symlink 会被静默跳过**；但 `fs.existsSync(oriPath)` 会跟随链接，若 `Pic/<date>/Ori` 本身是指向别处的 symlink，该目录会被当成清理根并**跟随进入** | `cleaner-service.ts:113-116`、`191-220` |
| 跨文件系统 | 不判断，纯递归 | `180-226` |
| 正在写入/占用 | 无特殊处理，`unlinkSync` 失败即 `warn` 跳过（Linux 下正在写的文件一般删得掉，Windows 下会被占用） | `196-205` |
| 失败统计/上报 | **只进日志**。`cleanDirectory` 返回的 `{files,size}` 只累计成功项；即使 90% 失败，`/clean` 仍回 `code:0` + 「清理完成」 | `cleaner-service.ts:180-226`、`api-service.ts:140-150` |
| 并发 | 无锁。但清理走**同步 fs**（`readdirSync`/`unlinkSync`），会把整个 Node 事件循环卡住，等于被动串行 | `cleaner-service.ts:191-224` |
| 误删保护 | 只有「分类开关」粒度；`File` 默认开启，与其它缓存同级，没有额外确认 | `types.ts:76-88` |

结论：这个插件的安全模型是「**靠路径拼死 + 用户自己勾选**」，不是「靠校验」。它没有把 `dataPath` 当信任边界。

## 4. D. 定时机制（我们不做，但坑值得记）

| 项 | 行为 | 依据 |
| --- | --- | --- |
| 频率 | `daily`（默认）/`weekly`/`interval` | `schedule-service.ts:39-58`、`types.ts:28-29` |
| 默认时刻 | `cronHour ?? 3`、`cronMinute ?? 0` | `schedule-service.ts:146-147` |
| 每周默认 | `frequencyValue ?? 0` → **周日**（JS `getDay()` 语义，前端也是「日一二三四五六」下标） | `schedule-service.ts:42`、`CreateTaskModal.tsx:192` |
| 间隔默认 | `frequencyValue || 3` 天 | `schedule-service.ts:47` |
| 时区 | 纯本地时间（`setHours`），无 TZ 配置；`lastRun` 存 ISO(UTC)，interval 分支再用本地 `setHours` 覆盖，DST 切换会漂 | `schedule-service.ts:27-58`、`106` |
| 调度实现 | 每次 `setTimeout(delay)` 触发后重排下一次；插件卸载时 `clearInterval/clearTimeout` 全清 | `schedule-service.ts:60-74`、`126-130` |
| 并发保护 | **无**。`runScheduleTask` 没有任何 running 标记；手动「立即执行」也不查上一次是否还在跑 | `schedule-service.ts:79-112`、`194-219` |
| 已知坑 | `setTimeout` 最大延迟 `2^31-1 ms ≈ 24.8 天`，超了会**立即触发**。作者用前端 `max=24` 硬截断来回避（注释里明写） | `CreateTaskModal.tsx:218-222` |
| 失败处理 | 单账号异常被 `try/catch` 记一条、继续下一个；整体结果只写 `lastResult` 字符串 | `schedule-service.ts:91-109` |

对「手动一次性清理」的启示只有两条：**别引入长延时定时器**（24 天溢出是真实存在的坑）；**若要定时，必须自己加锁 + 落盘 lastRun**，否则重启即丢。

## 5. E. 它做了、而我们可能没想到的

1. **只读预估（事实上的 dry-run）**：`scanCache()` 只 `stat` 不删，`/stats/:uin?retainDays=N` 同时返回「当前占用」与「按保留期可释放」两份数据（`cleaner-service.ts:269-305`、`api-service.ts:59-96`）。这是它最有价值的设计——先算再删。
2. **前后对账**：`/clean` 返回 `totalFiles/totalSize` 并按分类拆分（`api-service.ts:120-150`），定时任务把结果写进 `lastResult`（`schedule-service.ts:104-109`）。
3. **分类开关**：10 个布尔开关，把「日志」与「媒体」「接收文件」分开（`types.ts:4-16`），`enableNapCatData` 默认 **false**（`types.ts:85`）——唯一的默认关闭项，说明作者也认为动 NapCat 数据目录风险更高。
4. **配置持久化**：`config.json` 存默认选项 + 任务列表（`utils.ts:53-77`），WebUI 可改（`api-service.ts:166-175`）。

以及几个「它没做」的：

| 缺什么 | 证据 |
| --- | --- |
| 白名单/黑名单（除分类开关外无路径级排除） | `types.ts:4-16` 只有布尔 + `retainDays` |
| 体积阈值触发（「超过 N GB 才清」） | 同上，无相关字段 |
| 删除失败重试 | `cleaner-service.ts:203-205` |
| 配置校验（负数/超大值/非整数） | `api-service.ts:112` 直接展开合并 `body.options` |
| 保留最近 N 份日志 | `log` 分类同样走 `retainDays`，没有「保留最近 1 个文件」 |
| 预估数字的正确性 | `/accounts` 里 `estimatedCleanSize` 被**硬编码成 `'0 B'`**（`api-service.ts:33,38`），前端若读这个字段会一直显示 0 |

还有一处文档与代码不一致：v1.1.0 release notes 写「新增对 NapCat 运行日志的自动识别与清理」，但当前代码里**没有任何指向 `<NapCat目录>/logs` 的路径**（`cleaner-service.ts:91-175` 全量清单见 §1.1）。发布说明不能当行为依据。

## 7. 对我们的借鉴清单

### 7.1 照抄（保留现有做法）

| 结论 | 来自哪个发现 |
| --- | --- |
| **按 `mtime` + 保留天数删，不按目录名判断新旧**。插件把 `YYYY-MM` 写死成路径通配已经是风险点，若再按目录名决定生死，目录命名一变就会整片误删或整片不删 | §1.2、§2 |
| **清理前先只读统计、给出「将删除 N 个文件 / 预计释放 X」，再二次确认**。插件的 `scanCache` + `/stats` 就是这个角色，只是它把「确认」交给了 WebUI；我们做成了终端二次确认，更严 | §5.1 |
| **日志与媒体分开处理**：`nt_data/log`、`log-cache`、NapCat 自身 `logs` 属于纯诊断数据，整清风险低；`Pic/Ptt/Video` 才需要保留期。插件只有分类开关、日志也走 `retainDays`，我们把它固定为整清是合理的简化 | §1.1、§5.3 |
| **`File` 单独提示**：插件把 `File` 与其它缓存同级默认开启（`types.ts:81,85`）；我们的「接收文件可能是唯一副本，单独问一句」比它稳，应保留 | `types.ts:76-88` |

### 7.2 避开（明确不要跟着做）

| 结论 | 来自哪个发现 |
| --- | --- |
| **不要用「uid → md5 猜目录名」定位账号**，直接 `nt_qq_*` 通配逐个枚举。`md5(md5(uid)+"nt_kernel")` 是逆向出来的实现细节，QQ 一改算法就失效；而插件的退化分支「取第一个 `nt_qq_*`」在多账号下会清错号 | §1.3、`utils.ts:20-24`、`cleaner-service.ts:41-59` |
| **不要只清 `Pic/<date>/Ori`**。插件漏了 `Pic/<date>/Thumb`，也不清日期目录下的平铺文件——这正是「清完还占几百 M」的典型来源。用「递归、不关心层级、只按文件类型与 mtime 过滤」更抗目录结构变化 | §1.4、`cleaner-service.ts:139-145` |
| **不要把删除失败吞进日志**。插件哪怕全失败也回「清理完成」，用户只能翻后台日志。我们的做法是逐目录判返回码、汇总失败目录数并给非零退出，这个差异要保留 | §3、`api-service.ts:140-150` |
| **不要引入 `setTimeout` 长延时定时**。`2^31-1 ms ≈ 24.8 天` 的上限会让「每 30 天清一次」立刻触发，插件是靠前端 `max=24` 打补丁绕过的 | §4、`CreateTaskModal.tsx:218-222` |
| **不要跟随符号链接**。插件对遍历中的 symlink 是跳过的，但根目录若是 symlink 会被跟随；我们的 `find -xdev` + 只删 `-type f/-type l` 且不递归软链，语义更可控，别改成 `rm -rf` | §3、`cleaner-service.ts:113-116`、`191-220` |

### 7.3 不需要

- **独立 dry-run 接口 / WebUI 仪表盘**：我们是一次性交互脚本，「统计 → 确认 → 删除 → 对账」已经覆盖同等能力。
- **分类 JSON 配置 + 持久化**：十个布尔开关对 shell 交互是过度设计；三个菜单项（7 天 / 30 天 / 自定义）+ `File` 单独确认就够了。
- **白名单/黑名单、体积阈值、失败重试**：插件自己都没有；对「手动、低频、有人盯着屏幕」的场景收益很低。

### 7.4 值得回头核对的三个缺口（本次调研新发现）

1. **`NAPCAT_BASE_DIR/temp` 很可能是个空转项**：NapCat 真正的 temp 是 `~/.config/QQ/NapCat/temp`（`napcat-core/index.ts:190`），安装目录下并没有 `temp`。当前脚本会 `-e` 判断后跳过，属于「不出错但也不生效」。
2. **`logs` 的定位正确，但依赖「没设 `NAPCAT_WORKDIR`」**：`path.ts:18-26` 决定 `writePath`；本仓库启动方式（`Manage/NapCat.sh:43` 直接跑 `qq`，未导出该变量）成立，若用户自行设置了该变量，日志会跑到 `$NAPCAT_WORKDIR/logs`。
3. **未覆盖的候选目录**：`{hashDir}/nt_temp`（插件会清）、`{dataPath}/NapCat/temp`、`{NapCat目录}/cache`（解密库副本）。这三个都要**先实测确认存在与体积**再决定要不要纳入，尤其 `cache` 里可能是数据库副本，不能顺手删。

## 8. 未验证 / 限制

- **未在有 QQ 数据的 Linux 机器上实测**：本文所有目录层级（`Pic/<YYYY-MM>/Ori` 等）来自插件源码的**假设**，不是对真实 `nt_data` 的 `find` 结果。若某版本 QQ 改成 `YYYY-MM-DD` 或去掉日期层，插件的日期通配会静默失效——这一点由源码推出，但没有反例样本。
- **`log-cache`、`nt_temp`、`NapCat/data` 是否真实存在**：无法从一手来源确认；`NapCat/data` 在 NapCat 代码里找不到创建点（`napcat-core/index.ts:188` 只创建 `NapCat/` 与 `NapCat/temp`），怀疑是历史遗留配置项。
- **Winston `maxFiles: 5` 的精确语义**（是「保留 5 个轮转文件」还是「含当前共 5 个」）未实测；本文只确认 `maxsize: 5MB`、`maxFiles: 5` 两个参数值（`log.ts:155-156`）。
- **`{NapCat目录}/cache` 会不会在正常运行中持续增长**未验证：`reader.ts` 是数据库扫描工具的路径，不确定默认运行链路会不会走到。
- **官方文档的插件白名单页面不存在**：`napneko.github.io` 的插件文档（`/develop/plugin/`、`/develop/plugin/publish`）里没有「白名单」字样，白名单只能从 `loader.ts:12-19` 源码确认。
- **issue 样本极少**：插件仓库总共 4 条 issue，只有 #4 是真实用户反馈（且是「为什么没清我的 9.9G 数据库」这种误读），拿不到「删不掉 / 误删 / 权限」的系统性样本。NapCatQQ 仓库搜 `clean_cache` 命中 0 条。
- 未评估 Windows 侧行为（本项目只面向 Debian 系 Linux）。
