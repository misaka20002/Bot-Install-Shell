# GitHub 加速镜像与源可用性 —— 实测记录（2026-09-29）

> ⚠️ 本文件是一次**实测快照**，不是长期结论。镜像站波动很大——同一天两次测「直连 github.com」
> 都能得出相反结果（见 §2.3）。建议每 1~2 周按 §5 的脚本复测一次，并**另建带日期的文件**或在本文件追加新日期的小节，
> 不要把这份数据当永久事实引用。

## 0. 结论速览

- **本项目该用哪个**：本项目分发的是几十～几百 KB 的 `.sh`（`Manage/*.sh`），主流镜像都够用；
  当前 `Manage/Main.sh` 里配的是 `https://gh-proxy.com/`。若更在意大文件吞吐，实测首选
  **`gh-proxy.at9.net`（583 KB/s）** 与 **`gh.xmly.dev`（496 KB/s）**，两者都支持 clone 且内容与基准一致。
- **只看状态码会选错源**：`ghproxy.cn`、`mirror.houlang.cloud` 返回 200，但内容其实是它们自家首页，
  **根本不是代理**——这类最容易骗过「只看 HTTP 状态码」的检测。
- **下载后必须校验**：实测有中转站（`proxy.vvvv.ee`）返回 2875 字节，而真实文件 2831 字节、sha256 不一致，
  说明它改写了下载内容。本项目的分发链路是 `bash <(curl -sL …)` **直接执行**下载到的脚本，
  这类改写等价于**远程代码执行**，必须比对字节数 / sha256。
- **镜像的价值是「稳」而不是「快」**：直连 `github.com` 是**间歇性**可用（§2.3），
  镜像真正解决的是成功率，速度只是附带指标。

## 2. 三个高价值发现

### 2.1 抓到中转站改写文件（安全 · 最重要）

- `proxy.vvvv.ee` 返回 **2875 字节**，而真实文件是 **2831 字节**，sha256 与基准不一致 → 它往下载内容里插了东西。
- 同一批里 `gh-proxy.at9.net`、`gh.xmly.dev`、`cors.isteed.cc` 三家的 sha256 与基准**完全一致**。
- 结论：**下载 `.sh` 前必须比对字节数 / sha256**；对不自建的中转站，默认按「不可信管道」对待。

### 2.2 小文件评测会误导选型

- 所有镜像在**小文件**上都在 1~3s 内完成，看起来「大家都一样」。
- 换成 6MB 的包后差距立刻暴露：`gh-proxy.at9.net` 用 10s 跑完；`gh-proxy.com` 只有 95KB/s；
  `ghproxy.net` 29KB/s——两者都超时没下完。
- 已用**第二个文件复核**，差距真实存在，不是缓存或单次抖动。
- 推论：选型评测必须同时跑小文件与大文件（本项目是 `Manage/Main.sh` ≈ 50KB 与
  `Manage/Hapi_Claude_Manage.sh` ≈ 200KB 这一档，属于「小」的一端）。

### 2.3 直连 `github.com` 是间歇性的（更正上一轮结论）

- 上一轮结论曾写成「直连恒定不通」，**该结论作废**：22:52 测全超时，22:10 连续 4/4 次 200（1.55s）。
- 所以镜像的价值在于**稳定**；也说明任何单次测试都只能代表当时那一刻。

同批测试里的两个补充结论：

- 超时：`ghfast.top`、`mirror.ghproxy.com`、`gh.llkk.cc`
- **假 200（重点）**：`ghproxy.cn`、`mirror.houlang.cloud` 状态码正常但内容是自家首页 —— 不是代理。

## 3. 安全提醒

- **不要在镜像站登录 GitHub 账号**，也不要在请求里带 token。
- **不要用 `git config --global url.<mirror>.insteadOf https://github.com/`**：`--global` 会污染**所有**仓库
  （包括内网 GitLab）。建议只在单个仓库里配，或者像本项目一样只把镜像当「下载前缀」拼在 URL 前面。
- 本项目**不往用户全局 git 配置里写任何东西**：`Git_proxy` 只是 shell 变量，出问题删掉即可，没有残留。

## 4. 本项目侧的源可用性事件（gitee 451）

同一天还发生了一起与镜像选型相邻的事故，一并记在这里（细节与规则见 `AGENTS.md`
「镜像源与『现场拉取再执行』入口」）：

- **现象**：CN 服务器上 `xdm cc` 报 `/dev/fd/63: line 1: The: command not found`。
- **原因**：gitee raw 对 `Manage/Hapi_Claude_Manage.sh` 返回 **HTTP 451**，body 只有一行
  `The content may contain violation information`；而分发入口是 `bash <(curl -sL …)`，
  **没有 `-f`、没有内容校验**，于是这行纯文本被当成脚本执行，第一个词 `The` 成了命令。
- **拦截面（逐个文件 curl 核对，同日）**：

  - `Manage/Hapi_Claude_Manage.sh`：最新提交 451；更早的三个提交都是 200
  - `Manage/OtherFunctions.sh`、`AGENTS.md`、`Manage/BOT-PlugIn.sh`：新、旧提交都 451
    （其中 `BOT-PlugIn.sh` 在本仓库**没有任何引用**，属孤儿文件）
  - 其余 14 个 `Manage/*.sh`：全部 200

- **关键性质**：gitee 的拦截判定是**按对象（blob）**的，不是整仓封锁——同一个文件可以
  「新推送的那版 451、历史版本依旧可下载」。所以「gitee 上这个仓库坏了」是错判，正确动作是**换源**。
- **处置**：`Manage/Main.sh` 里三处拉取入口改为「GitHub 源 + `${Git_proxy}`」（`xdm cc`、主菜单 `H`、
  主菜单 → BOT → 其他功能）；在 gitee 上仍返回 200 的脚本保持走 gitee；
  并 bump `version` 与 `Main.sh` 的 `old_version`（否则 `xdm` 自更新判据不成立，服务器拿不到新脚本）。

## 5. 复测方法（可重跑）

⚠️ 两个前提：① **必须在目标机器上测**（CN 服务器 / 海外节点结论不同，开发机连不通不代表站点失效）；
② **小文件与大文件都要测**（§2.2）。

```sh
# 基准：直连 raw 的字节数与 sha256
URL="https://raw.githubusercontent.com/misaka20002/Bot-Install-Shell/master/Manage/Main.sh"
REF_BYTES=$(curl -sL "$URL" | wc -c)
REF_SHA=$(curl -sL "$URL" | sha256sum | cut -d' ' -f1)
printf '基准: %s 字节  sha256=%s\n\n' "$REF_BYTES" "$REF_SHA"

# 逐个前缀代理：状态码 / 耗时 / 字节数 / 内容是否与基准一致
for p in "https://gh-proxy.at9.net/" "https://gh.xmly.dev/" "https://cors.isteed.cc/" \
         "https://gh-proxy.com/" "https://ghproxy.net/" "https://ghproxy.cn/"; do
  info=$(curl -sL --max-time 30 -w '%{http_code} %{time_total}s' -o /tmp/probe.bin "${p}${URL}")
  b=$(wc -c < /tmp/probe.bin)
  s=$(sha256sum /tmp/probe.bin | cut -d' ' -f1)
  if [ "$s" = "$REF_SHA" ]; then verdict="内容一致"; else verdict="❌ 内容不一致（被改写或返回了别的页面）"; fi
  printf '%-26s %s  %s 字节  %s\n' "${p#https://}" "$info" "$b" "$verdict"
done
rm -f /tmp/probe.bin

# clone 能力（部分镜像只代理 raw，不支持 git clone → refs 403）
git ls-remote "https://gh-proxy.at9.net/https://github.com/misaka20002/Bot-Install-Shell" refs/heads/master
```

判定口径：

- **只看状态码会误判**：`200` 也可能是自家首页（§2.3），必须比对字节数 / sha256。
- **`451` = 被源站拦截**（内容审核），换源即可，不要在原地等它恢复。
- **clone 必须单独验**：`git ls-remote … refs/heads/master` 能列出 sha 才算支持 clone。
