# Codex 凭据语义修复 + 测试框架加速（2026-10-19）

> 状态：①~④ 已随本次提交落地；⑤（测试框架加速）待实施。
> 本文是把 2026-10-19 这一轮对话的结论固化成 spec，作为后续改动与复盘的依据。

## Problem Statement

用户在 `Hapi_Claude_Manage.sh` 里填了 `OPENAI_API_KEY`，启动 Codex 却报：

```text
Codex error: Codex thread entered systemError
Codex error: Missing environment variable: OPENAI_API_KEY.
```

同一时间「查看配置」里只显示 `******`，用户无法判断 Key 到底有没有写进去。另外两个附带问题：

1. 菜单 3「新建配置（不切换）」完全不问 1M 上下文窗口，产物与菜单 1 不一致。
2. 菜单 1 与菜单 3 对「关闭 1M」的语义不一致（一个只删自己写的默认值，一个完全不支持），
   而同类工具 cc-switch 是「关掉就删干净」，用户在两处看到不同结果。

## Solution

- **把第三方 Key 的落点从 `env_key` 换成 provider 段的 `experimental_bearer_token`**，并显式写
  `requires_openai_auth = false`。`env_key` 在 Codex 里只从**进程环境变量**取值，`auth.json` 完全不参与；
  这正是上面那条报错的唯一来源。
- **第三方模式下移除 `~/.codex/auth.json`**（Key 已经在 config.toml 里），移除前把官方登录态原样暂存；
  切回官方端点（或 auth.json 消失）时自动放回。与 cc-switch `preserve_codex_official_auth_on_switch = false` 对齐。
- **移除菜单 7**（写入/编辑官方 auth.json）：官方登录改由 cc-switch 的授权中心绑定，脚本不再承担登录编辑。
- **菜单 3 补上 1M 提问**，与菜单 1 共用同一个提问函数；关闭 1M 改为**无条件删除**两个顶层键（对齐 cc-switch）。
- **「查看配置」类预览直接显示明文 Key**（6 个入口），校验/报错路径继续打码。
- **写入后自检**：回读 Codex 实际会用的 Key 并打印，另提供可选的 `${base_url}/models` 连通性探测。
- **测试框架加速**：把「每个断言 fork 一次」改为「一次 node 进程算出所有计数」，目标是把 Windows/MSYS 上的
  套件耗时砍半以上。

## User Stories

1. 作为使用者，我想在第三方 base_url 下填完 Key 就能直接启动 Codex，而不需要自己去 `export OPENAI_API_KEY`。
2. 作为使用者，我想让「填过的 Key」在 config.toml 里看得见，这样我能确认它真的写进去了。
3. 作为使用者，我不想在「查看配置」里看到 `******`——那让我无法区分「没填」和「填了但没生效」。
4. 作为使用者，我填完 Key 后想立刻看到一行「Codex 会使用这个 Key：…（长度 51）」，而不是只看到「已写入」。
5. 作为使用者，我想可选地用这个 Key 请求一次 `${base_url}/models`，确认端点与 Key 都通。
6. 作为使用者，我想在切换第三方配置时**不丢失**我原来的 ChatGPT 登录态。
7. 作为使用者，我想在切回官方端点时自动恢复之前暂存的登录态，而不用重新登录。
8. 作为使用者，我想在 cc-switch 里绑定官方登录后，本脚本不会把它删掉或覆盖。
9. 作为使用者，我不想再看到「写入/编辑官方 auth.json」这个菜单项——那件事已经交给 cc-switch 的授权中心。
10. 作为使用者，我想在「新建配置（不切换）」时也被问到 1M 上下文窗口。
11. 作为使用者，我想在关闭 1M 时两个顶层键被彻底删掉，而不是「有时留着、有时删掉」。
12. 作为使用者，我想让菜单 1 和菜单 3 产出的配置结构一致（同样的 provider 段、同样的凭据字段）。
13. 作为使用者，我想让老配置里的 `env_key` 在我下一次填 Key 时被自动迁移，而不是继续报缺环境变量。
14. 作为使用者，我想在切换已有配置时，老配置的 `env_key` 也被顺手迁移。
15. 作为使用者，我想在没有可迁移 Key 时**不要**被删掉 `env_key`（那可能是我自己在用环境变量）。
16. 作为使用者，我想在 provider 段里有 token 时，`requires_openai_auth` 一定是 `false`，避免 ChatGPT token 被发到第三方端点。
17. 作为使用者，我想在配置库里保存第三方配置时不需要 auth.json（它本来就不存在）。
18. 作为使用者，我想在切换一份「auth 为空」的配置时，live 的 auth.json 被移除而不是写进一个 `{}`。
19. 作为维护者，我想让测试在 Windows 上跑得够快，能在一次改动后跑完整个套件而不是只敢跑单组。
20. 作为维护者，我想让测试断言不再依赖「每个断言 fork 一个 grep」这种 Windows 上最贵的操作。
21. 作为维护者，我想删掉与个人使用场景无关的过度安全测试，缩短反馈时间。
22. 作为维护者，我想让 `AGENTS.md` 与代码保持一致，避免下一个 agent 照着「菜单 7」的旧说明改代码。

## Implementation Decisions

### 凭据落点（核心）

- 第三方 provider 段写 `experimental_bearer_token = "<key>"`，并显式 `requires_openai_auth = false`。
  新建段与更新已有段都走这一条；更新时**原位替换** `env_key` 行以保持字段顺序。
- 只要段内存在 token，就把 `requires_openai_auth` 收敛为 `false`（残留的 `true` 会让 Codex 拿 ChatGPT 凭据请求第三方）。
- 迁移只发生在「能拿到 Key」时：调用方传入的 Key > 段内已有 token > auth.json 的 `OPENAI_API_KEY`。
  三者都没有时只警告、不删 `env_key`。
- `hapi_codex_current_value` 的 `OPENAI_API_KEY` 读取顺序改为「config.toml 段内 token 优先，auth.json 兜底」。

### auth.json 的去留

- 判定依据是**写完之后**的 config.toml：当前 `model_provider` 指向自定义段、且段内有 token ⇒ 第三方模式。
- 第三方模式：如果现有 auth.json 带登录材料（`chatgpt` / `chatgptAuthTokens` / 有 `tokens`），整份存进
  `~/.codex/hapi_login_stash.json`（0600），然后删除 auth.json；纯 apikey 的 auth 不暂存（Key 已在 config.toml）。
- 官方目标 + 填了 Key：先暂存登录态，再整份写成 `{ auth_mode: "apikey", OPENAI_API_KEY: key }`
  （混合 tokens + Key 会让 Codex 继续走 OAuth）。
- 官方目标 + 没填 Key：仅当 auth.json 不存在且暂存存在时恢复。恢复失败（暂存损坏）只报错，不删除暂存、不中止写入。
- `route-only` 路径完全不碰 auth.json。

### 路由判定的一处补充

- 「没有登录材料、也没有新 Key、但用户明确给了官方端点」现在判为 `official`（原来是 `legacy`）。
  否则第三方模式删掉 auth.json 后，用户填官方端点会被建成一个没有凭据的 custom 段，也永远走不到「恢复登录态」。

### 菜单 7 移除

- 删除菜单项与整块函数：官方 auth 编辑器、编辑器探测/运行辅助、auth 文件规范化写入、路由状态报告。
- 所有引用「菜单 7」的提示文案改为指向 cc-switch 授权中心或「修正该文件」。
- `hapi_check_codex_auth_file` 保留两级校验（`official` / `loadable`），`loadable` 仍用于配置库存取。

### 1M 上下文窗口

- 提问抽成共用函数，菜单 1 与菜单 3 都调用；提示语走 stderr，函数只输出 `1m` / `off`。
- 菜单 3 生成的配置里，两个 1M 键必须落在**第一个 section 之前**（顶层）。
- 关闭时无条件删除两个顶层键（只认顶层；section 内同名键不动）。理由：1M 是一个开关，不是一个用户字段；
  要保留自定义值就不要回答「否」。

### 预览与自检

- 6 个「查看配置」入口（Claude live / Claude 配置库 / Codex live / Codex 配置库 + 两处 TOML 视图）不再脱敏。
  校验/诊断输出（`hapi_check_codex_auth_file`）继续按命中规则打码。
- 写入完成后回读并打印「Codex 会使用的 Key」及其长度；读不到时明确报红。
- 可选连通性探测：只打印 HTTP 状态码，不打印响应体；默认关闭（很多中转站没有 `/models`）。

## Testing Decisions

- 只测**外部可观察行为**：config.toml / auth.json / 暂存文件的内容，以及命令返回值与提示文案；
  不断言内部函数名或实现细节（唯一例外是「已删除函数不得复活」这类结构性回归）。
- 主 seam 仍然是「写入器 + 菜单入口」，不新增 seam：所有断言都通过实际调用菜单函数或写入器，
  再读磁盘产物。
- 回归点：
  - 第三方写入：段内有 token、无 `env_key`、`requires_openai_auth = false`、auth.json 被移除、登录态被暂存；
  - 官方写入：auth.json 为 apikey 模式、第三方路由被剥离并暂存；
  - 老配置迁移：`env_key` → token；拿不到 Key 时保留 `env_key` 并警告；
  - 1M：菜单 1 开/关、菜单 3 开/关、route-only 字节级零改动；
  - 预览：明文显示 Key、不再出现 `******`；校验输出仍然打码；
  - 菜单 7：函数与菜单项都不存在。
- 现有套件（`tests/Hapi_Claude_Manage/run.sh`）按 A~L 分组，本次修改了 D/E/G/H/I/J/K/L 七组的断言。
- 加速方案（待实施）：
  - 把断言实现从「每条 `grep -c` 子进程」改为「一次 node 调用批量返回所有文件的匹配计数」；
  - 断言只登记 `(文件, 正则, 期望条数)`，真正的计数在分组末尾统一执行；
  - 保留现有的隔离、超时、日志三条保证，以及失败时的可读输出。

## Out of Scope

- 不实现官方 ChatGPT 登录的写入/刷新（交给 cc-switch 授权中心）。
- 不改 `requires_openai_auth = true` 这类「第三方端点 + OpenAI 认证」的特殊用法（本脚本只做直连第三方）。
- 不改 Claude Code 侧的取 key 语义，只把预览从打码改成明文。
- 不改 `hapi`（hub）本身的启动方式与环境注入。

## Further Notes

- 结论来自对 cc-switch 4.0.15 源码的核对：第三方 Key 写 `experimental_bearer_token`、`requires_openai_auth`
  跟随「磁盘上有没有登录」、默认切换第三方时删除 auth.json。官方 config reference 也写明
  `env_key` 只从环境变量取值、`experimental_bearer_token` 是「直接把 token 写在表里」。
- 与 cc-switch 的唯一有意差异：本脚本没有 per-provider 数据库，路由与登录态都靠单槽暂存文件维持。
- 用户明确要求「减少不必要的安全测试」：后续会删掉与本机个人使用无关的过度断言（例如对 0600 的多路径重复覆盖），
  但**保留**校验路径打码、备份 fail-fast 这两类「防数据丢失」断言。
